How the RAG Arm Is Implemented

Dense retrieval (bi-encoder + FAISS) → context assembly → the same LLM → structured parsing. Every step below points at the source file that implements it.

1. Offline: turn the corpus into a searchable index

Step 0 · Build the corpus and guard against leakage

scripts/prepare_data.py → src/vlab/data/pubmedqa.py · dedup_corpus()

The corpus comes from PubMedQA's pqa_artificial subset (600 documents); the test set is held-out pqa_labeled (60 questions). The two must be isolated: any corpus document sharing a pid or an identical question with a test record is dropped. Otherwise retrieval could surface the very abstract the gold answer was derived from, and the RAG arm's score would be meaningless.

Step 1 · Encode and persist the index

scripts/build_index.py → src/vlab/data/corpus.py · Retriever.build()

texts = [f"{question}\n{context}" for row in corpus]          # title + abstract encoded together
emb = SentenceTransformer("BAAI/bge-small-en-v1.5").encode(
        texts, normalize_embeddings=True).astype("float32")   # unit vectors, 384 dims
index = faiss.IndexFlatIP(dim)                                # flat inner-product index
index.add(emb)                                                # 600 x 384 ~ 0.9 MB

Two deliberate choices: vectors are L2-normalized so the inner product equals cosine similarity and scores read as 0–1 semantic affinity; and a flat index rather than IVF/HNSW, because at this scale exact search is fast and deterministic — reproducibility beats an approximate index for a controlled experiment.

2. Online: retrieve and generate per question

Step 2 · Query encoding and search

src/vlab/data/corpus.py · Retriever.batch_retrieve()

vectors = encoder.encode(questions, normalize_embeddings=True)
scores, ids = index.search(vectors, top_k=2)   # top_k from configs/*.yaml

Questions and documents share the same bi-encoder (symmetric retrieval). Batched encoding plus one matrix search means retrieval for all 60 questions is nearly instantaneous — the wall-clock cost is entirely in generation.

Step 3 · Assemble the prompt

src/vlab/arms.py · build_prompts() → src/vlab/prompts.py · rag_prompt()

texts = [clip(d["text"], cfg.retriever.max_doc_chars) for d in docs]   # 700 chars/doc
prompt = rag_prompt(question, texts)                                   # attach context

One hard-won lesson lives here: the first version placed the evidence between the question and the Answer: cue, and the 0.5B model lost the thread and emitted a single word (RAG accuracy 0.283). Reordering to instruction → format → question → evidence → Answer: — keeping the answer trigger last — lifted the same arm to 0.450. This is the lost-in-the-middle effect, amplified in small models.

Step 4 · Generate and parse

src/vlab/backends.py · Generator.generate() → src/vlab/prompts.py · parse_prediction()

All arms share one Generator: greedy decoding, max_new_tokens=64, batch 16, chat template applied. Only the sft/sft_rag arms additionally attach a LoRA adapter (PeftModel.from_pretrained, weights not merged), so the comparison isolates where knowledge comes from rather than decoding differences. Output parsing extracts Verdict: / Conclusion: with a keyword-matching fallback, because small models improvise.

3. A real example (run, not fabricated)

pid 21645374 Question: Do mitochondria play a role in remodelling lace plant leaves during programmed cell death?

Retrieved documents (similarity scores look deceptively high):

#scoreDocument openingRelevance
10.724Does transcriptional profiling of Arabidopsis root hairs and pollen define an apical cell growth signature?off-topic
20.721Does pINK1 trigger autocatalytic activation of Parkin to specify cell fate decisions? (PINK1-Parkin regulates mitochondria)weak

The assembled prompt (~1.8k characters) goes to the model:

You are a biomedical research assistant. Answer the research question with a short
verdict followed by a one-sentence conclusion.

Respond in exactly two lines:
Verdict: <yes|no|maybe>
Conclusion: <one sentence>

Question: Do mitochondria play a role in remodelling lace plant leaves during
programmed cell death?

Use the abstracts below as evidence.

Evidence:
[1] Does transcriptional profiling of Arabidopsis root hairs and pollen define an
apical cell growth signature? Current views on the control of cell development are
anchored on the notion that phenotypes are defined by networks of transcriptional
activity. ...
[2] Does pINK1 trigger autocatalytic activation of Parkin to specify cell fate
decisions? The PINK1-Parkin pathway is known to play important roles in regulating
mitochondria dynamics, motility, and quality control. ...

Answer:

Model output: No  ·  Gold: yes  wrong

This example is the experiment's core finding. Biomedical abstracts are superficially similar to each other: across all 60 questions the top-1 cosine score never dropped below 0.537 (mean 0.717), yet most retrieved documents were unrelated — the 600-document corpus simply does not contain the test abstracts. High similarity is not relevance, so RAG keeps injecting confident but irrelevant evidence.

Read the three numbers together:

  • The evidence itself works — the oracle arm reaches 0.683 > prompt_only 0.617: putting the right knowledge in context does help.
  • The bottleneck is retrieval, not the generator — real RAG gets 0.450, below no-evidence prompting. The 23.3-pt gap to the oracle is entirely retrieval missing the right document.
  • Irrelevant evidence is worse than no evidence — it anchors the model on a confident but wrong trail.
